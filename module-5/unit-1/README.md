# Unit 1 Lab: Pipeline Orchestration with GitHub Actions

___

Solution walkthrough: https://youtu.be/pmwDrLVJuDQ

## Scenario

Your engineering squad has just inherited a shared code repository containing a set of automated configuration check scripts.  
The previous team attempted to automate these checks using a GitHub Actions workflow configuration file located at `.github/workflows/ci.yml` within the codebase.  
However, developers are complaining that the continuous integration process is incredibly slow and regularly breaks without providing clear, immediate feedback.  

Upon initial inspection of the workflow file, you notice two critical structural flaws:

1. The sequence violates the Fail Fast principle by executing a heavy, slow container build process before running lightweight code quality checks.
1. The workflow is failing at runtime due to an underlying syntax issue within the codebase.

Your objective is to optimise the pipeline orchestration to fail fast, diagnose the failure using local terminal logs, and fix the codebase to achieve a successful, verified pipeline execution.


===

## Task 1: Run the workflow

In this workshop, you will be using an open source tool called `act`.  
Instead of committing code to a remote repository and waiting for a cloud provider to allocate a worker node, act reads your GitHub Actions workflow files and runs them directly on your local workstation inside Docker containers.  
This provides instant feedback and prevents broken experiments from cluttering your repository history.

1. Open the terminal application and ensure you are working within the root directory of the provided project repository.
1. Execute the following command to start the local continuous integration runner: `act`.
1. Watch the terminal output carefully. You will notice the tool pulling down the necessary Docker images and starting the jobs defined in your workflow.
1. Allow the process to run until it fails. Pay close attention to how much time elapses before the terminal reports the failure.

===

## Task 2: Analyse the Structural Bottleneck

Now that you have observed the pipeline failing slowly, you need to understand why it was orchestrated this way.  
A continuous integration pipeline is simply a set of automated instructions.  
If these instructions are executed in the wrong order, the pipeline becomes a major bottleneck for the development team.

1. Open the workflow file with Vim: `vim .github/workflows/ci.yml`.
1. Scroll down to the jobs or steps section of the YAML file.
1. Identify the sequence of execution. You will see that a heavy, slow task (such as building a Docker container image or compiling complex dependencies) is listed before the lightweight tasks (such as running static code analysis or linting checks).

===

## Task 3: Implement the Fail-Fast Principle

To resolve the bottleneck you just identified, you will apply the "Fail Fast" principle.  
This core methodology states that the fastest and least resource-intensive quality checks should always run first.  
If a fast check fails, the pipeline aborts immediately, saving time and valuable cloud computing resources.

1. Inside your text editor, carefully highlight the entire block of YAML code responsible for the linting or syntax check.
1. Cut and paste this block so that it sits above the container build step in the sequential order.
1. Ensure your YAML indentation is correct after pasting. YAML is strictly reliant on spacing, so ensure the new steps align perfectly with the surrounding blocks.
1. Save the `.github/workflows/ci.yml` file.
1. Return to your terminal window.
1. Execute the local runner command again: `act`.
1. Observe the live execution logs.

===

## Task 4: Diagnose and Fix the Codebase Error
The pipeline is now highly efficient, but the application source code is still broken.  
As a DevOps engineer, you will often need to parse raw console logs to help developers identify exactly where their code is failing.  
Visual UI dashboards might show a red "failed" badge, but the raw text logs hold the actual solution.

1. Scroll through the terminal output generated by your previous failed run.
1. Read the logs from the bottom up, looking for the specific output generated by the static analysis linter.
1. Locate the error trace. The linter will explicitly state the name of the Python file, the exact line number, and the specific syntax error (e.g. an unexpected indent or a missing bracket).
1. Open the offending Python file in your text editor.
1. Navigate to the line specified in the logs, fix the syntax mistake, and save the file.

===

## Task 5: Verify a Successful Green Run
The final step in any pipeline orchestration task is to verify that all components work together harmoniously to produce a successful outcome.  
You have optimised the pipeline structure and fixed the application code; now you must prove the system is stable and ready for deployment.

1. Return to your terminal for the final time.
1. Execute the local runner: `act`.
1. Monitor the output as it progresses through the entire workflow sequence.
